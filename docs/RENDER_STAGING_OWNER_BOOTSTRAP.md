# Одноразовый владелец admin на Render Free — без Shell

## Границы разрешения

Этот документ — инструкция, а не разрешение на запуск. Требуются отдельные
подтверждения владельца на публикацию кода, изменение Render, deployment и
создание владельца в тестовой БД. До подтверждения ничего из нижеследующего не
выполнять. Production, main, основной сервис и его БД не затрагиваются.

Целевой сервис: `fleetai-security-staging`.
Целевая страница: `https://fleetai-security-staging.onrender.com/auth/login`.
Ветка: `security/hermes-finance-readonly-20261106`.

## Что делает код

- `python -m fleetai.staging_start` сначала проверяет окружение, НЕ импортируя
  модули БД и приложения до завершения проверки.
- При неверной конфигурации процесс завершается до инициализации БД.
- Только после подтверждения идентичности сервиса, HTTPS-origin и PostgreSQL
  приложение создаёт/обновляет свою схему обычным механизмом. Legacy seed
  отключён: реальные номера машин и закупочные значения не копируются.
- При `FLEETAI_BOOTSTRAP_OWNER_ENABLED=1` пароль читается из переменной
  `FLEETAI_BOOTSTRAP_OWNER_PASSWORD`, используется общий helper `fleetai.auth`
  и scrypt. В БД хранится только хеш. Логин фиксирован: `admin`.
- Существующий `admin` и его пароль НЕ изменяются. Другой существующий владелец
  вызывает отказ без переименования или сброса. Единственность также защищена
  ограничением БД, включая конкурентные вставки.
- Bootstrap не создаёт финансовые операции, машины, сессии входа, credentials
  Hermes или HTTP-маршруты регистрации. Не выполняет отправки в интеграции.
- Перед запуском Gunicorn временные bootstrap-переменные удаляются из окружения
  процесса; пароль не передаётся в аргументах. Запускается один worker.
- Без включённого флага владелец не создаётся. Стандартные `app.py` и Procfile
  остаются прежними; bootstrap не подключается к обычному production-start.

## 1. Подтвердить сервис и изоляцию БД

В Render проверить именно новый тестовый сервис и отдельный PostgreSQL-ресурс.
Сверить ID ресурса БД, hostname, имя базы и подключения основного сервиса через
панель, не выводя DSN/пароли в чат или логи. Не использовать production-копию.
У тестовой БД должны быть только синтетические данные.

Записать несекретные идентификаторы в настройки только тестового сервиса:

- `FLEETAI_STAGING_SERVICE_ID`: фактический `srv-...` этого тестового сервиса;
  он должен совпадать со встроенным `RENDER_SERVICE_ID`.
- `FLEETAI_STAGING_DB_HOST`: фактический Render hostname отдельной тестовой БД
  (внутренний `dpg-...-a` либо соответствующий внешний hostname Render).
- `FLEETAI_STAGING_DB_NAME`: фактическое имя этой отдельной базы.
- `FLEETAI_STAGING_DB_CONFIRMED=1`: только ПОСЛЕ проверки ресурса через Render.

Совпадение имён и этот флаг сами по себе не доказывают изоляцию: они фиксируют
предварительную проверку оператором. Если нельзя подтвердить отдельный ресурс,
остановиться; не включать bootstrap.

## 2. Окружение только тестового сервиса

Постоянные настройки:

- `FLEETAI_PUBLIC_BASE_URL=https://fleetai-security-staging.onrender.com` —
  без завершающего слеша, пути, query, fragment или учётных данных.
- `DATABASE_URL`: защищённое подключение приложения к проверенной тестовой
  PostgreSQL с явно заданным `?sslmode=require` либо `?sslmode=verify-full`.
  Если URL уже содержит параметры, не приписывать второй `?`: нормализовать
  URL в защищённом поле; допускается только один параметр `sslmode`.
- Если задан `PUBLIC_BASE_URL`, он должен точно совпадать с HTTPS-origin выше.
- Встроенные Render `RENDER=true`, `RENDER_SERVICE_NAME`, `RENDER_SERVICE_ID`
  и `PORT` не подменять вручную. Сервис должен называться точно
  `fleetai-security-staging`.
- Debug/testing должны быть выключены. Не задавать development `FLASK_ENV`.
- Не переносить банковские, Telegram, SMS, Wialon и cron-секреты. Непустые
  `TBANK_*`, `TELEGRAM_*`, `SMSRU_*`, `WIALON_*`, `CRON_SECRET` отклоняются.
- Не задавать `PG*` или `GUNICORN_CMD_ARGS`: скрытые переопределения соединения
  и параметров сервера отклоняются.

`FINANCE_READONLY_DATABASE_URL` не нужен для создания владельца. Если он задан,
он обязан указывать на ту же тестовую БД с отдельным пользователем. Эта проверка
НЕ подтверждает SELECT-only привилегии: настройка и проверка финансовой роли и
выпуск отдельного токена Hermes — самостоятельный этап. Без read-only datasource
новый финансовый API должен оставаться fail-closed, а не использовать writer.

Временные настройки, добавляемые только после разрешения создать владельца:

- `FLEETAI_BOOTSTRAP_OWNER_ENABLED=1`
- `FLEETAI_BOOTSTRAP_OWNER_PASSWORD`: собственный уникальный пароль, от 12 до
  1024 символов, вводимый владельцем в защищённое поле Render. Значение нигде
  в этой инструкции не задаётся. Не отправлять его в чат, Git или логи.

## 3. Публикация и запуск — только после отдельного разрешения

1. Проверить, что Auto-Deploy отключён для тестового сервиса. Если он включён,
   НЕ выполнять push до согласования: push способен запустить deployment.
   Изменение этой настройки также требует разрешения владельца.
2. Опубликовать проверенный локальный коммит только в указанную security-ветку,
   без force и без merge/main. Сам по себе локальный SHA недоступен Render.
3. Убедиться, что Source Branch тестового сервиса — указанная security-ветка.
   Основной сервис и его настройки не менять.
4. Build Command: `pip install -r requirements.txt`.
5. Start Command: `python -m fleetai.staging_start`.
6. Только после подтверждения настроек, изоляции и создания владельца выполнить
   ручной deploy проверенного SHA тестового сервиса. Shell и pre-deploy job
   не используются. Не создавать и не повышать тариф ресурсов без согласования.
7. Если запуск отказал, сначала проверить безопасную диагностику конфигурации
   и идентификаторы ресурсов. Не отключать проверки и не включать debug.

Ожидаемые сообщения не содержат секретов:

- `Staging bootstrap: created` — владелец создан;
- `Staging bootstrap: already-exists` — прежний admin сохранён;
- `Staging bootstrap: disabled` — bootstrap выключен;
- `Staging startup refused: ...` — безопасная причина отказа конфигурации;
- общий отказ без traceback — ошибка БД/инициализации, подробности намеренно
  не выводятся, чтобы не раскрыть параметры соединения.

## 4. Проверка и обязательное удаление временных секретов

1. Открыть целевую HTTPS-страницу `/auth/login` и войти как `admin` со своим
   паролем. Пароль вводится в браузере владельца, не через Telegram.
2. При необходимости проверить `/auth/session`: `kind=owner`. Не запрашивать
   финансовые сводки ради проверки входа: legacy GET могут начислять аренду.
3. После успешного создания удалить ОБЕ переменные
   `FLEETAI_BOOTSTRAP_OWNER_ENABLED` и `FLEETAI_BOOTSTRAP_OWNER_PASSWORD`
   из Environment именно тестового сервиса. Не хранить их в общих Environment
   Groups. Если они уже поступают из общей группы, остановиться и согласовать
   изоляцию: не менять группу, используемую основным или другими сервисами.
4. Сохранить настройки и согласованно перезапустить/redeploy только тестовый
   сервис, чтобы прежний процесс больше не имел исходного окружения Render.
5. Повторить вход тем же паролем. Владелец и хеш в БД сохраняются; отсутствие
   временных переменных не отключает обычную авторизацию.

Удаление ключей из `os.environ` НЕ удаляет их из настроек Render: удаление в
панели обязательно. Приложению не выдаётся административный API-ключ Render
для автоматической очистки. После удаления переменных и рестарта одноразовый
механизм не активируется, даже если строка владельца когда-нибудь исчезнет.

## Проверки реализации

Только изолированная SQLite внутри `.test-data`, синтетические значения,
запрещённые внешние подключения и перехваченный exec Gunicorn. Тестирование не
является запуском на Render и не подтверждает фактическую изоляцию его БД.
Проверяются preflight, scrypt, идемпотентность, сохранение другого владельца,
очистка окружения, существующий HTTPS-login/cookies, отсутствие bootstrap HTTP
route, неизменность всех строк не-auth таблиц и прежние auth-сценарии.
