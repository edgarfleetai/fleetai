# FleetAI: изолированная приёмка безопасности перед тестовым развёртыванием

Область: ветка `security/hermes-finance-readonly-20261106`; авторизация владельца/водителя, привязки Telegram, границы доступа и отдельный API Hermes. Этот документ не разрешает merge в main, Render deployment или использование production.

## Обязательная конфигурация стенда

- Собственная пустая PostgreSQL с синтетическими данными. Никогда не копировать production DSN, секреты, документы водителей или финансовые записи.
- `PUBLIC_BASE_URL` — явный канонический HTTPS origin тестового стенда, например `https://staging.example.invalid`; без userinfo, пути, query или fragment. В deployed mode отсутствие корректной настройки не должно разрешать login/CSRF по переданному Host.
- Терминатор TLS должен передавать корректный исходный Host; backend не должен становиться публичным HTTP-входом. Произвольные клиентские Forwarded/X-Forwarded-* не являются доказательством авторизации или Origin.
- Owner session: непрозрачная серверная сессия; `__Host-` cookie с Secure, HttpOnly, SameSite=Lax, Path=/ и без Domain. Ответы API/auth/driver — no-store, nosniff, no-referrer. HSTS задаётся по явной HTTPS-конфигурации, не по X-Forwarded-Proto.
- `FINANCE_READONLY_DATABASE_URL` — отдельная роль с CONNECT/USAGE и SELECT только необходимых финансовых таблиц, без DML/DDL, TEMP, административных ролей и наследуемых write-привилегий. Роль не должна читать таблицы сессий или хешей credentials. Обычная проверка bearer приложением использует его отдельное auth-соединение, а не наделяет финансовую роль доступом к auth-таблицам.
- Никаких реальных Telegram/bank/SMS/Wialon credentials на приёмке. Входящие интеграции либо отключены fail-closed, либо используют только локальные заглушки и синтетические значения.

## Инварианты исправлений

1. Финансовый запрос водителя, документ и инициирование банковского платежа заново проверяют сессию/epoch/binding под общей блокировкой точного сохранённого автомобиля. Это изменение допуска, не изменение суммы, комиссии, подписи, зачисления или расчёта аренды.
2. Финансовый JSON полностью формируется до снятия блокировки. Вложенные начисления в этой транзакции выполняют flush, а не ранний commit. Обычное владельческое legacy-поведение сохранено.
3. Если отзыв назначения завершился первым — старому запросу отказ без данных и без банковского вызова. Если запрос первым захватил блокировку — формируется снимок прежнего назначения, а переназначение ожидает его завершения.
4. Неоднозначные сохранённые коды автомобилей, совпадающие после trim, не позволяют водителю получить сессию/билет или данные. Уникальный индекс `auth_car_code_trim_unique` атомарно запрещает новые совпадающие ключи, включая конкурентную вставку. При уже существующих дублях обновление схемы отказывает до запуска приложения. Никакие коды и реестры автоматически не переписываются; исправление существующих данных требует отдельного решения.
5. Hermes имеет только `finance:read`, не использует owner-cookie fallback и не допускается к legacy финансовым API. Чтение новых API не запускает rent sync, сверку/начисления, внешние оплаты или уведомления.
6. HTTP 403 и 405 оба могут означать корректный запрет записывающего метода; проверка не ограничивается статусом и должна доказывать отсутствие handler invocation и изменений в БД.

## Автоматические проверки

- Штатный pytest в `.venv-security`, с очищенным окружением, запрещёнными внешними транспортами и отдельным `.test-data`.
- `security_checks/native/`: opt-in приёмка настоящего PostgreSQL/psycopg/QueuePool, повторяемой инициализации схемы, реальных ожиданий row lock, обоих порядков конкуренции, истечения сессии во время ожидания, ABA, rollback, одноразовых ссылок и SELECT-only роли. Не импортировать этот harness как часть SQLite-only `tests/conftest.py`.
- `security_checks/https/`: opt-in локальная TLS/proxy приёмка с собственным временным сертификатом и проверкой его доверия, только loopback endpoints, синтетическая база и отключённые исходящие интеграции.
- Все ключи, конфигурации соединения, кластеры, сертификаты и логи запусков — вне Git. Временные серверы должны останавливаться, файлы паролей и ключей удаляться независимо от результата.

## Что не считается проверенным автоматически

- Подключение к Render, production SHA/расписания, фактический внешний ingress и существующие роли production.
- Реальные финансовые операции, конкурентная идемпотентность банковских webhook и договорные бизнес-сценарии за пределами проверенного security diff. Их бизнес-логику этот этап не изменяет.
- Устаревший корневой `parser.py` содержит исходную `IndentationError` (строка 187), неизменную относительно базового коммита. Рабочий entrypoint `app.py` загружает пакет `fleetai`, а маршруты — `fleetai.parser`; эти активные модули проходят синтаксическую и runtime-проверку. Переписывание legacy-парсера финансовых заметок не включено в security-этап.
- Отсутствие немаркированных исторических тестовых записей или полная банковская сверка. API сохраняет unverified/reconciliation_required и не складывает несопоставимые реестры.

Готовность определяется свежими фактическими результатами всех трёх наборов, независимым review и совпадением хэшей проверенного кода с сохраняемым коммитом. Одобрение локальной приёмки означает готовность к отдельному синтетическому стенду, а не разрешение на production.
